# Automation Sandbox __TAG__

Preview NuGet package artifact release. Rolls up the work merged since `v0.2.0-beta.6`.

## Breaking Changes

None. Every change in this release is additive - no existing public member was renamed, removed,
or had its signature changed. See `docs/release-notes/unreleased-public-api.md` for the running
staging note this release clears.

## Highlights

- **Product direction reversed: web and desktop are equal-priority platforms (#469, superseding
  #402).** The freeze `v0.2.0-beta.6` placed on intent planning, test generation, and new LLM
  providers is lifted - active feature work continues on all three. The engine's safety posture
  (evidence gate, per-component name/descendant gates, LLM independent-agreement quorum,
  Hallucination Guard) is unaffected; only the roadmap/scope framing changed.
- **Two packages ship for the first time: `AutomationSandbox.ContentAnalysis` and
  `AutomationSandbox.IntentExecution`.** Both existed on `main` before this release but were never
  part of a tagged build; this is their first appearance in a published release.
- **Content-quality reporting across a multi-page scan (#471).**
  `ContentAnalysisReportFileSink`/`ContentAnalysisReportDocument`/`ContentAnalysisReportEntry`/
  `ContentAnalysisReportHtmlRenderer` accumulate `ContentAnalyzer` findings as an append-only JSON
  Lines log plus an HTML dashboard, the same pattern `HealingReportFileSink` uses (#424) -
  `ContentAnalysisReportEntry.FromAnalysis` builds one page's entry directly from an
  `AnalyzeAsync` result. `ContentAnalyzer.CountPassages` reports how much text a page actually had,
  so a scan returning zero passages on a page expected to show text reads as a likely
  capture-timing bug, not a clean page.
- **`SiteCrawler`: point the engine at a URL instead of hand-authoring per-page navigation
  (#475).** Walks a site breadth-first from one starting URL, same-origin by default, bounded by
  `SiteCrawlOptions` (`MaxPages`/`MaxDepth`), with a per-page callback as the hook for content
  analysis or any other work - `SiteCrawler` itself has no dependency on `ContentAnalysis`. A page
  that fails to navigate or capture is recorded in `SiteCrawlResult.Failures`, not aborting the
  whole run. Deliberately read-only: it follows `<a href>` links only and never clicks anything -
  guessing which button on a page is "probably" a language switcher and clicking it blind is a
  correctness and safety risk, not just a missing feature (see `docs/web-automation.md`'s
  real-world example for why, verified live against several unmodified production sites).
- **Dynamic content: `PlaywrightWebSession.WaitForTextChangeAsync`/`WaitForTextAsync` (#475/#480).**
  A DOM capture is a point-in-time snapshot; `WaitForVisibleAsync` alone does nothing for content
  that re-renders in place (a SPA language switch, an async-loaded value) on an element that was
  already visible. These wait for the matched element's text to actually change, or to reach a
  specific expected value.
- **`Wait` steps can wait for expected text, not just visibility - across web and desktop alike
  (#480/#482/#483).** `Wait` steps reuse `AssertionKind.TextEquals`/`TextContains`
  (`ExpectedValue`) - otherwise only meaningful on `Assert` steps - instead of a new
  `IntentActionType`, so no planner or codegen cascade was needed. Live web execution,
  `PlaywrightCSharpTestGenerator`, `PlaywrightTypeScriptTestGenerator`, and
  `FlaUiCSharpTestGenerator` all honor it identically; `AssertionKind.None` (the default) keeps the
  original visibility-wait behavior, so this is additive, not a behavior change for existing
  scenarios.
- **Two new runnable samples.** `samples/SiteContentAuditQuickstart` chains `SiteCrawler` →
  `ContentAnalyzer` → `ContentAnalysisReportFileSink`: given a URL, crawl the site and write a
  JSON/HTML content-quality report; with no arguments it audits a bundled fixture site with
  planted findings (the CI-verified mode). `samples/DesktopAppExplorerQuickstart` points
  `Discovery`'s `ApplicationConnector`/`UiTreeWalker` at any real Windows desktop app by exe path
  or process name and reports its locator health (empty/duplicate `AutomationId` counts) - compile
  cross-target-verified from Linux CI, not yet runtime-verified against a live external
  application ([#489](https://github.com/mustafasercansak/automation-sandbox/issues/489), tracked
  and open).

## Fixes

- **Content-analysis false positives on code samples (#479):** `ContentAnalyzer` no longer treats
  `<pre>`/`<code>` subtrees as prose - source code identifiers and deliberate markers like
  `// TODO` were reading as spelling/duplicate-word/placeholder defects. Found by running the new
  content-audit sample against this project's own published docs site.
- **`Wait` step timeout unit mismatch (#481):** a `Wait` step's timeout `Value` meant seconds in
  live web execution (`IntentWebExecutor`) but milliseconds in all three code generators - the
  same scenario, live-executed vs. turned into a generated test, meant two different real-world
  wait durations. It is milliseconds everywhere now; `IntentWebExecutor` calls the exact same
  parsing helper the generators use instead of re-implementing it, which is what prevents this
  class of drift recurring.
- **A live 404 on the published docs site:** `_config.yml`'s `exclude: docs/nuget` entry was
  silently matching `docs/nuget-packaging.md` too by path-prefix, 404ing that page since it was
  added. Found and fixed during a full documentation audit that also corrected stale package
  counts, broken cross-references, and out-of-date behavior descriptions across `AGENTS.md`,
  `README.md`, and `docs/`.

## Known Limitations

- **Calibration:** higher confidence thresholds reduce false heals, but the magnitude does not
  transfer between applications. Calibrate against your own UI history; the shipped
  `MinimumConfidence` is `0.50`.
- **Accuracy:** the per-component gates (#370, #375, #416) drive deleted-element false heals to
  zero on both committed fixtures at no measured auto-heal recall cost, but this is not a general
  absence detector - see `benchmark-calibration.md` §15 for the one documented residual scenario
  and why it isn't closed.
- **External validation:** all benchmark evidence remains synthetic mutations over two real
  application trees (HandBrake, ShareX). No external user integration or organic (non-synthetic)
  drift dataset exists yet; #401 explicitly blocks 1.0 on this and the evidence bar it requires -
  now covering both web and desktop integrations - is documented in `external-validation.md`.
- **Interactive discovery:** `SiteCrawler` finds pages via `<a href>` links only. A language
  switcher (or any other state change) implemented as a JS-only button/dropdown with no `href`
  requires an explicit scripted step (`ClickAsync` + `WaitForTextChangeAsync`/`WaitForTextAsync`,
  or an `IntentScenario` `Wait` step with `AssertionKind`) - this is a deliberate safety boundary,
  not a gap intended to be closed by guessing which elements to click.
- **LLM providers:** covered by mocked-HTTP unit tests; the nightly workflow gates one known
  ground-truth agreement scenario against independent providers. Release creation does not run a
  live gate.
- **Platform:** desktop automation is Windows-only (FlaUI / UIA3). The heuristic engine and the
  web path are cross-platform and verified on Linux in CI. Linux desktop discovery via AT-SPI
  (#17) and macOS via AXUIElement (#373) remain research notes, not shipped backends.
